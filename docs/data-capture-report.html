3. How the data is protected (verified on production)

RiskSafeguard and production result
Bots skipping the bot checkThe bot-check cookie is signed by the server and expires after 2 h; a hand-written turnstile_verified=true is rejected and cannot start a survey. pass
Starting without consent開始實驗 stays disabled until 「我已閱讀並同意參與本研究」 is ticked; the server refuses to create a submission without a consent record. pass
Network error while saving an answerThe participant stays on the scenario with 「儲存失敗，請再按一次。」 and the retry saves it; nothing is skipped. pass
Network error on the final 送出Stays on the email step with 「提交失敗，請稍後再試」; code, email and Q1–Q8 are kept for the retry. pass
Refreshing the page mid-studyResumes on the same page with the same session, also after a fast first answer; refreshing the debrief keeps the same payout. pass
Changing an answer afterwards (Back button or API)Rejected; the first confirmed answer stays. pass
Completing a submission twice / swapping the email afterwardsRejected; email, answers and completion time unchanged. pass
Missing code, malformed email, incomplete questionnaireThe server rejects the completion and stores nothing. pass
Payout shown ≠ payout paidDebrief, debrief after reload, email page, database and payment ledger all show the same amount. pass

4. Who can read what

  • Registration code, email, Q1–Q8, consent and device are returned only with an admin login; anyone else gets nothing, including through the participant API. verified
  • Both exports are admin-only. Both now contain the email, so both are identifying files.
  • Unsent questionnaire answers and the consent tick live only in the participant's browser tab until they are sent.

5. Know before you analyse

  1. Q1–Q8 are true / false, with true = the first option (同意 / 好 / 管制). For Q8, true means 管制 (restrict).
  2. Response time = milliseconds from the scenario appearing to the confirm click that saved the answer, including revealing the edges and moving the slider. A page refresh restarts the clock for that scenario. The test robot answers in ~1.2 s; the manual participant took 4–30 s.
  3. Device type is mobile when Chrome reports a mobile device or the user agent says Mobile / Android / iPhone / iPad, otherwise desktop; it describes the device that started the submission. The full user agent is kept for finer grouping.
  4. Consent Version names the consent text the participant saw (currently welcome-2026-11-18); it changes whenever that text changes.
  5. Presentation order: participants see their scenarios in the order of the answers array (also given by Answered At), not in the order the session lists them.
  6. Answered At in the research CSV is a raw epoch-milliseconds number (e.g. 1795059162125), unlike the other time columns, which are ISO dates. It is exact; convert with as.POSIXct(x/1000, origin="1970-01-01") or pd.to_datetime(x, unit="ms").
  7. Partner decisions are random draws: no real partner answer is used (BUG-008, left as is by decision; the manual run logged matched=0/20).
  8. Same person, two devices: a second device with an already-used registration code is accepted and paid (EC-8; the ledger lists the code twice). Check the payment ledger for repeated registration codes and mark duplicates invalid before paying.
  9. Participants who stop part-way keep their saved answers (Submission Completed = false) and are in the research CSV but not in the payment ledger.
